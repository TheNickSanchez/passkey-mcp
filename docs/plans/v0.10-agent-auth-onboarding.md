**Product & Security Architecture Plan — Agent Authorization Modes & First-Run Onboarding (`v0.10`)**

**Baseline:** `v0.9.2` (`entries.json` v2 zero-Keychain metadata index, `pk1:` inline sharing, `LAContext` Touch ID, and `(ancestor_pid, start_time)` session leases already live on `main`).

---

**1. Problem Statement & Product Philosophy**

`passkey` already implements a 1Password-grade biometric session engine (`policy = session` in `passkey/leases.py` + `LocalAuthentication.framework` in `passkey/auth.py`), yet almost no user experiences it by default because:
1. Every new or migrated entry silently hardcodes `policy = "allow"` (`models.py`), hiding Session Touch ID behind `N` manual `passkey policy <entry> session` commands.
2. First-run onboarding (`passkey` FTUE and `passkey init`) never asks the user how they want AI agents authorized to use their credentials.
3. Users with dozens of entries have no single command to switch between **Session Touch ID** and **YOLO / Headless (`allow`)** mode—or to keep background IDE-boot MCP servers headless (`allow`) while gating CLI/agent entries (`jamf`, `aws`, `stripe`, `gh`) with **1-tap Session Touch ID**.

**Design Inspiration (`1Password CLI` Model):**
* Per-tool-call prompting (`prompt`) on everyday coding keys causes severe prompt fatigue during 20-turn agent loops.
* Silent global `allow` gives zero human-in-the-loop signal when an autonomous agent starts using a sensitive integration (`jamf`, `intune`, `stripe`).
* **10-minute process-tree Session Touch ID (`session`)** is the sweet spot for agentic workflows, paired with **Scoped Headless (`allow`)** for background stdio MCP servers launched automatically at IDE startup.

---

**2. Proposed Feature Specification**

**2.1 Global Default Policy Setting (`passkey config default-policy`)**
* Add `default_policy` (`"allow" | "session" | "prompt"`) to `<data_dir>/settings.json` (`passkey config default-policy <mode>`):
  * **`session`** *(Recommended on macOS when Touch ID / `LAContext` is available)*: **1 Touch ID tap** unlocks the credential for the calling agent/terminal process tree (`10m` default via `agent-session-lease-ttl`).
  * **`allow`** *(YOLO / Headless — default on Windows or headless Linux)*: **0 Touch ID prompts**; secrets remain protected at rest in the OS Keychain, scrubbed on `stdout`/`stderr` by `SecretMasker`, and guarded by HMAC `.env.passkey` repo trust.
  * **`prompt`** *(Strict Step-Up)*: Touch ID required on **every** invocation unless an explicit `passkey lease grant` is active.
* Wire `passkey new`, `passkey request` (when `--policy` is omitted), and `passkey upload` (when creating a net-new entry with default `"allow"` policy) to inherit `get_default_policy()`.

**2.2 First-Run Onboarding Prompt (FTUE)**
* During first-run interactive onboarding (`passkey` States A/B when `settings.json` has not yet recorded an explicit `default_policy` choice):
  * Ask a single 3-option `questionary.select` question:
    1. `Touch ID once per 10m agent session (Recommended — like 1Password)` -> `default_policy = "session"`
    2. `Auto-approve / YOLO (zero prompts — fastest for local dev & background MCP)` -> `default_policy = "allow"`
    3. `Strict Touch ID on every single command (maximum lock-down)` -> `default_policy = "prompt"`
  * Persist the selection atomically to `<data_dir>/settings.json` so onboarding never asks twice.

**2.3 Background MCP Server Split in `passkey init`**
* When an IDE (Cursor, Claude Desktop, VS Code) launches, it spawns all wrapped stdio MCP servers in parallel. Setting `policy = session` on 6 background stdio MCP servers would trigger 6 concurrent prompts at IDE startup.
* `passkey init` keeps wrapped stdio MCP server entries on `policy = "allow"` by default (unless `--policy session|prompt` is explicitly passed) and prints a clear one-line note showing how to opt specific high-privilege MCP servers (e.g., `passkey policy jamf session`) into Session Touch ID.

**2.4 Bulk Policy Management (`passkey policy --all`)**
* Upgrade `passkey policy`:
  * `passkey policy --all <allow|session|prompt> [--exclude-mcp] [-y|--yes] [--json]`
  * Updates all entries (or skips `source == "import-mcp"` when `--exclude-mcp` is passed) across both the OS Keychain and the `entries.json` v2 metadata index in one pass, allowing instant switching between **YOLO (`allow`)** and **Session Touch ID (`session`)**.

**4. Follow-Up Patch (`v0.10.1`) — Zero-Keychain `O(1)` HMAC-Signed Policy Store**

* **Problem Observed on Live macOS (`31` entries under `uv tool`):**
  1. `cmd_policy_all` called `get_all_entry_metas(hydrate_unmigrated=True)`, triggering `N` sequential `keyring.get_password` calls on unhydrated entries before even reaching the `[Y/n]` confirmation prompt.
  2. `bulk_update_policies` and `cmd_policy <entry> <mode>` read and rewrote every individual Keychain secret item (`N` `get_password` + `N` `set_password` calls). Because macOS Keychain binds per-item ACLs to the exact Python binary that originally created each item, touching `31` older items from `uv tool`'s managed Python triggered `31` back-to-back `securityd` password popups (`-128 Keychain Access Denied` on cancel).
* **Architecture (`<data_dir>/policies.json` + Single `__policy_hmac_key__` Root):**
  1. Reserve `"__policy_hmac_key__"` in `RESERVED_NAMES` (`passkey/models.py`).
  2. Store authoritative policy overrides in `<data_dir>/policies.json` (`0o600`, atomic temp + `os.replace`, guarded under `_metadata_lock()`) signed with `HMAC-SHA256` and anchored by a single `~165`-byte Keychain item `(SERVICE, "__policy_hmac_key__")` containing `{"v": "pk_policy_v1", "k": "<64-hex-key>", "digest": "<64-hex-sha256>", "count": <int>}` (with `.policy_hmac_key` `0o600` fallback only when `keyring` raises `KeyringError` and `policies.json` does not yet exist; raise `KeychainAccessError` if `policies.json` exists and Keychain IPC fails without fallback). Ignore non-`"pk_policy_v1"` mock strings when `policies.json` is absent so legacy unit-test `MagicMock`s remain compatible.
  3. **`O(1)` Zero-Secret-Touch Policy Updates:**
     * `cmd_policy_all` uses `get_all_entry_metas(hydrate_unmigrated=False)` (`0` Keychain calls before `[Y/n]`; `--exclude-mcp` inspects live wrapped MCP client configs via `_get_wrapped_mcp_entry_names()` plus hydrated `meta.source`).
     * `set_entry_policy(name, policy)` and `bulk_update_policies(entry_names, policy)` update `<data_dir>/policies.json` + `__policy_hmac_key__` + `entries.json` v2 in one lock pass **without reading or writing any user secret Keychain item** (preserving `hydrated=False` on unhydrated rows and full `Entry` metadata when hydrated). `handlers.py` resolves `EntryMeta` (`hydrate=False` when setting policy) so single-entry `passkey policy <entry> <mode>` also touches `0` user secret Keychain items.
  4. **Tamper, Rollback & Deletion Defense + Lifecycle Sync:**
     * `_get_entry` overlays verified `policies.json` onto `entry.policy` before `_backfill_entry_meta(entry)` so all secret consumers (`run`, `exec`, `inject`, `mount`, `get`, `edit`, `rotate`, `export`, `share`) see the authoritative policy and self-heal `entries.json` if `entries.json` was edited on disk.
     * `authorize_entry_access` verifies `policies.json` integrity against `__policy_hmac_key__` (including detecting `rm policies.json` when `__policy_hmac_key__` has `count > 0`, raising `PasskeyError` on edit, rollback, or deletion tampering).
     * When `policies.json` already exists on disk, `save_entry` syncs `policies[entry.name] = entry.policy` and `delete_entry` removes `name` (when `policies.json` does not exist yet, `save_entry` does not create it, preserving `0` extra Keychain calls in `TestZeroKeychainMetadataIndex`).
     * Update `SECURITY.md` and `docs/06-Security-and-Biometrics.md` to document `<data_dir>/policies.json` + `__policy_hmac_key__`, and add `policy_integrity` verification in `passkey/doctor.py` (`run_diagnostics(deep=True)` when `policies.json` exists).
